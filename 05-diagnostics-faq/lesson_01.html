物理-网络-中间件-应用 四层隔离排障法

预计阅读 14 分钟 · 前置知识：了解系统基础软硬件配置 · 全程只读，不改变机器狗状态

🎙️ 展开直播口播导语（讲师版）

“在复杂的机器人系统中，当‘机器狗不动’或‘程序收不到数据’时，盲目重启或在代码里乱加 print 只会浪费宝贵的时间！老练的现场支持工程师手中都有一张‘故障定位地图’——从物理层、网络层、中间件层到应用层的四层分层隔离诊断法！哪怕遇到再离奇的灵异现象，跟着这张图走，3 分钟之内必定锁定根因！”

本课学习目标

  • 建立“物理 → 网络 → 中间件 → 应用”的自底向上排障顺序，不再盲目重启
  • 用指示灯、电量与关节温度快速判定物理层状态
  • 用 ping 与静态 IP 配置排除网络层故障，独立处理 Host Key 变更
  • 用 export ROS_DOMAIN_ID=178 与 Aorta CLI 探针验证中间件总线
  • 识别看门狗、CPU 饥饿、置信度未激活等应用层陷阱
  • 在故障问诊机器人中完成 4 类症状的即时定位演练

一、四层排障总览：先定位层级，再动手

机器狗不会说话，但它会在每一层留下证据。四层排障法的核心不是背命令，而是固定顺序：先确认物理链路，再确认网络可达，然后验证中间件总线，最后才怀疑业务代码。现场故障看似千奇百怪，根因几乎总能归入下面四层之一。

L1 · 第一层 物理层 Physical Layer
  • 指示灯不亮 / 网口灯不亮
  • 电量 < 15% 预警
  • 关节电机 > 75°C 降扭
L2 · 第二层 网络层 Network Layer
  • ping 不通 / SSH 超时
  • 本机 IP 误配 .2 冲突
  • Host Key 指纹变更
L3 · 第三层 中间件层 Middleware Layer
  • topic list 空空如也
  • echo 收不到报文
  • ACL 白名单静默丢弃
L4 · 第四层 应用层 Application Layer
  • 发包不足 10Hz 被刹车
  • 置信度全被过滤
  • CPU 被 AI 占满
← 先查这里：地基，一切通信的前提 业务表象，最后查 →
🧭 使用原则：每层只回答一个问题 物理层问“电与线好不好”，网络层问“包能不能到”，中间件层问“话题与数据在不在”，应用层问“业务逻辑对不对”。上一层不通时，不要在下层瞎改；每层先取证（看灯 / ping / topic echo），再改一个变量并回归验证。

诊断决策流程：三个入口，逐层收敛到处置

现场提问通常只有三类：“连不上”“没数据”“不动”。从对应入口进入，不需要跳层，沿着箭头走到处置即可。

① 连不上SSH 超时 / ping 不通

共同纪律：从物理层往上排查，每层先取证再动手；一次只改一个变量，改完立刻回归验证。

二、第一层：物理层（Physical Layer）

物理层不写代码，只看三件事：灯、电、温度。这一层异常时，上层所有命令都会表现得很“玄学”，所以永远从这里开始。

典型症状：整机无响应 指示灯不亮 网口灯不亮 步态无力、容易跪倒 红灯快闪、拒绝起立

检查清单

  1. 网口灯检查插上有线网卡后，观察转接头指示灯。绿灯常亮、黄灯闪烁代表物理电气链路正常；若灯不亮，换插 Type-C 接口或检查转接头芯片。
  2. 电量检查电量低于 10% 时，系统会限制大电流输出；总览清单以电量 < 15% 作为预警线。若电池指示灯红光快速闪烁、机器狗拒绝起立，说明已进入低压自保模式，应插上官方动力充电器，充至 30% 以上再测试。
  3. 关节温度检查若长时间高负荷测试导致任一关节电机温度超过 75°C，系统会触发自动降扭温控保护，表现为步态无力、容易跪倒。此时应关机静置散热 15 分钟。

判定标准

观察项正常判定异常处置
转接头指示灯绿灯常亮、黄灯闪烁 → 物理电气链路正常灯不亮：换插 Type-C 接口，检查转接头芯片或更换线缆
电量高于 15%，可正常测试< 10% 限制大电流输出；充至 30% 以上再测试
关节电机温度不超过 75°C> 75°C 触发降扭：关机静置散热 15 分钟
机身指示灯进入待命呼吸状态不亮或红灯快闪：先充电，再检查供电与线缆
⚠️ 物理层没解决，不要急着敲命令网口灯不亮时，ping 必然不通；关节已经 > 75°C 时，再怎么改代码也只会继续降扭。先让物理状态回到正常区间，再进入网络层。

三、第二层：网络层（Network Layer）

物理链路确认正常后，网络层只回答两个问题：电脑能不能到达 192.168.126.2，以及本机地址有没有和机器狗撞车。

典型症状：ping 不通 SSH Connection refused 或超时 REMOTE HOST IDENTIFICATION HAS CHANGED 能连 WiFi 却进不了主板

1. IP 冲突诊断

执行 ping 192.168.126.2。如果 ping 不通，首先检查电脑是否手抖将本机网卡配成了 192.168.126.2（自身与自身冲突）；正确配置应为 192.168.126.100。

bash 
ping 192.168.126.2
✅ 通的判定返回类似 64 bytes from 192.168.126.2: icmp_seq=1 ttl=64 time=0.8 ms，说明物理链路与 IP 路由已经畅通，可以继续查中间件层。
🚨 严禁本机使用 .2电脑网卡若配成 192.168.126.2，会与机器狗自身地址冲突，表现为两头失联。请改为 192.168.126.100。

2. SSH 密钥冲突报错

若提示 WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!，通常是由于借测了另一台机器狗，指纹不一致。这不是网络故障，而是 SSH 的防中间人攻击机制在拦截旧指纹。在本地电脑执行一键清理：

bash 
ssh-keygen -R 192.168.126.2

清除后重新执行 ssh vbot 即可。注意：这条命令在本地电脑执行，不是登录机器狗之后再执行。

3. 判定标准

检查项正常判定异常处置
ping 192.168.126.2稳定返回 64 bytes from 192.168.126.2，延迟毫秒级超时或不可达：回到物理层查灯与线缆，再查静态 IP
本机网卡地址192.168.126.100误配 .2 会与机器狗冲突，立即改回 .100
ssh vbot正常进入计算主板Connection refused 或超时：检查接线、是否连错 Wi-Fi、网卡 IP
Host Key 警告无警告执行 ssh-keygen -R 192.168.126.2 清除旧指纹

四、第三层：中间件层（Middleware Layer）

网络通了，不代表总线在说话。中间件层要看的是：所有终端是否在同一个 Domain、总线上有没有活跃话题、报文到底流不流。

典型症状：话题列表为空 能看到话题但收不到数据 服务列表缺失 自定义话题下游静默无数据

1. Domain 178 对齐

确保所有终端与脚本均已执行 export ROS_DOMAIN_ID=178。新开一个终端就忘一次，是现场最常见的“话题消失术”。

bash 
export ROS_DOMAIN_ID=178

2. Aorta 命令行万能探针

直接在主板终端使用 Aorta CLI 工具验证总线健康状态，三条命令按顺序执行：

bash 
# 1. 列出当前总线上所有活跃话题
aorta topic list

# 2. 采样 1 条 IMU 原始报文验证数据流
aorta topic echo /imu_raw --count 1

# 3. 列出所有可用服务
aorta service list
🔍 三条命令各管什么aorta topic list 证明“总线上有谁在说话”；aorta topic echo /imu_raw --count 1 证明“数据真的在流”；aorta service list 证明“服务端已经就位”。话题可见但 echo 无报文，问题通常在发布端、Domain 或 ACL，而不是网络。

3. ACL 拒绝静默丢弃

若向自定义话题发布数据但下游收不到，检查是否存在未授权的私有路由。EDU 默认仅允许 Schema 白名单内的话题，白名单外的话题可能被静默丢弃——没有报错，也没有数据，最容易被误判成“程序没跑起来”。

4. 判定标准

检查项正常判定异常处置
export ROS_DOMAIN_ID=178所有终端与脚本都在 Domain 178新终端重新导出；脚本内也要显式设置
aorta topic list能看到 /imu_raw 等活跃话题清单为空：先查 Domain，再确认中间件服务已启动
aorta topic echo /imu_raw --count 1收到 1 条 IMU 原始报文无报文：查发布节点、总线状态与 ACL
aorta service list列出可用服务缺服务：服务端未启动或 Domain 不一致
自定义话题下行话题在 Schema 白名单内不在白名单：申请合规路由，避免被静默丢弃

五、第四层：应用层（Application Layer）

物理、网络、中间件全部正常，机器狗还是“抽搐一下就不动”或“走着走着瘫倒”，就该查业务逻辑了。应用层最常见的三个坑：看门狗、置信度、CPU 饥饿。

典型症状：四肢抽搐一下即停 突然四脚朝天瘫倒 姿态关键点全被过滤 音频脚本 Permission Denied 相机画面延迟数秒

1. 发包频率抖动导致看门狗抽搐

检查发送循环是否加入了耗时的大型同步阻塞操作（如网络爬虫或高耗时图形绘制）。若发包间隔超过 0.5s，底层看门狗会自动刹车。必须将网络通信与运控拆解在独立线程中执行。

只向 /vel_cmd 发单包，机器狗会四肢抽搐一下就不动——这是看门狗在保护，不是执行器坏了。必须编写循环，以 10Hz ~ 20Hz 的频率持续发包。

⏱️ 0.5s 是生死线任何一次同步阻塞只要把发包间隔拖过 0.5s，看门狗就会按“失联”处理并安全停机。把日志上传、图像绘制、HTTP 请求之类操作挪出运控线程。

2. 人体姿态置信度遗漏了 Sigmoid 转换

若 /perception/poses 的所有关键点置信度都被过滤，通常是误把未激活的 Logit 实数当成了 0~1 的置信度概率。对 confidence 应用公式：

formula 
prob = 1 / (1 + exp(-logit))

应用 Sigmoid 之后，关键点置信度才会落在 0~1 区间，后处理阈值才有意义。

3. CPU 被占满导致运控进程饥饿

视觉 / 音频大模型占满 8 个 CPU 时，底层运控心跳会超时，机器狗可能走着走着突然四脚朝天瘫倒在地。使用 taskset -c 2-7 将 AI 脚本绑定至后置核心，给运控留出算力：

bash 
taskset -c 2-7

4. 判定标准

检查项正常判定异常处置
/vel_cmd 发包10Hz ~ 20Hz 持续循环，间隔稳定低于 0.5s单包或阻塞导致超时：改循环发包，拆独立线程
关键点 confidence经 Sigmoid 转换后位于 0~1全是 Logit 实数：应用 prob = 1 / (1 + exp(-logit))
CPU 占用运控进程不被 AI 负载抢占8 核被占满：taskset -c 2-7 绑定 AI 脚本
控制接口只使用官方标准速度接口 /vel_cmd/vbot/sportmode_cmd 在 1.6 已废弃，迁移至 /vel_cmd

八、本课小结

四层隔离排障法的价值，在于把“玄学故障”拆成四个可以独立验证的问题。记住顺序，现场就不会被表象牵着走。

层级一句话判定代表处置
物理层灯不亮、电不足、温度高充电至 30% 以上、关机静置散热 15 分钟、换线换口
网络层ping 不通、IP 冲突、Host Key 变更电脑改为 192.168.126.100；ssh-keygen -R 192.168.126.2
中间件层话题空、无报文、ACL 静默丢弃对齐 ROS_DOMAIN_ID=178；用 Aorta CLI 三连探针；核对白名单
应用层抽搐、瘫倒、置信度全 0、CPU 饥饿10Hz ~ 20Hz 持续发包、Sigmoid 转换、taskset -c 2-7
  • 排障顺序固定为物理 → 网络 → 中间件 → 应用，上一层不通不跳层
  • 物理层看灯、电、温度：电量 < 15% 预警，关节 > 75°C 降扭
  • 网络层用 ping 192.168.126.2 取证，本机地址永远是 .100
  • 中间件层先 export ROS_DOMAIN_ID=178，再用 Aorta 三连探针验证数据流
  • 应用层守住 0.5s 看门狗生死线，以 10Hz ~ 20Hz 循环发包
  • 每层取证、一次只改一个变量，改完立即回归验证
