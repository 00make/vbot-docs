一、360° 16 线激光雷达：建图与避障切片

机器狗腹部与顶部集成的高频激光雷达，持续以 10Hz 输出全向三维空间点云。它是一条标准的 ROS 2 话题，先认清参数再谈用法：

项目取值说明
线数 / 视场16 线 · 360° 全向部署在机器狗腹部与顶部的高频激光雷达
刷新率10Hz持续输出全向三维空间点云
ROS 2 话题/vbot/lidar/point_cloud点云数据的唯一入口
消息类型sensor_msgs/msg/PointCloud2标准三维点云消息
常用坐标系lidar_link 或 base_link点云坐标系通常绑定在这两者之一

点云切片：把三维降成二维再喂给避障

在板载 ARM64 处理器上，如果直接拿 10 万个三维点云去计算 3D 障碍物膨胀代价，CPU 占用率会瞬间突破 70%。推荐启动 pointcloud_to_laserscan 转换节点，将高度处于 [0.1m, 0.6m] 范围内的 3D 点云切片投影为二维雷达射线扫描包（sensor_msgs/msg/LaserScan）。算法开销骤降 80%，避障反应速度提升 5 倍！

保留：投影为二维 LaserScan 丢弃：带外高度的点不参与避障切片
0.1 m – 0.6 m
0.1 m 0.6 m 更高 →

高度标尺为示意：只有落在 0.1–0.6 m 高度带内的点，才会被投影成二维雷达射线。

建图与 Nav2 适配要点

  • 坐标系先对齐：点云坐标系通常绑定在 lidar_link 或 base_link，配置代价地图与坐标变换前先确认，避免“点云看着对、障碍物位置偏”。
  • SLAM 建图吃全量：需要完整三维结构时，直接订阅 /vbot/lidar/point_cloud（PointCloud2）。
  • Nav2 避障吃切片：避障只需要平面障碍，订阅 pointcloud_to_laserscan 转换出的 LaserScan，让 3D 膨胀代价不要落到 ARM64 上。
  • 一条数据两种形态：建图与避障并不冲突，同一个雷达话题可以同时供给“全量点云”和“切片扫描”两个下游。
⚠️ 性能红线别把 10 万个三维点直接塞进 Nav2 的 3D 障碍物膨胀代价：在板载 ARM64 上 CPU 会瞬间突破 70%，避障反应反而变慢。切片投影是这门课最划算的一次“降维”。

二、深度双目相机：H.265 硬件视频流解析

为了在板载百兆/千兆总线上稳定传输 1080P@30fps 双目画面，系统不在网络上直接广播无压缩的原始 BGR8 像素矩阵（未压缩双目码流高达 1.5 Gbps ~ 3.0 Gbps，会瞬间挤爆总线导致运动卡顿），而是采用硬件编码压缩：

画面规格1080P@30fps 双目画面
未压缩码流1.5 Gbps ~ 3.0 Gbps（会挤爆总线）

Python 实时解码与去畸变流水线

使用 av（PyAV）库配合板载硬件解码加速，开箱即用：

python 
import av
import cv2
import numpy as np

def decode_h265_frame(h265_bytes):
    """将接收到的 H.265 字节包解码为 OpenCV BGR 图像"""
    container = av.open(h265_bytes, format='h265')
    for frame in container.decode(video=0):
        # 转换为 NumPy BGR 矩阵
        img = frame.to_ndarray(format='bgr24')
        return img
    return None
代码行作用
av.open(h265_bytes, format='h265')把收到的字节包按 H.265 容器打开
container.decode(video=0)解码第 0 路视频流，逐帧产出
frame.to_ndarray(format='bgr24')转成 OpenCV 可直接使用的 NumPy BGR 矩阵
return None没有解出任何一帧时的兜底返回值
📌 关于“去畸变”这一环源文档把这一节命名为“实时解码与去畸变流水线”，示例代码覆盖的是解码环节——把 H.265 字节包还原成 BGR 帧。去畸变属于拿到帧之后的后处理，接在你自己的视觉代码里；cv2 与 numpy 之所以在示例中导入，正是为后续处理留好接口。
⚠️ 别把原始像素扔上网络未压缩双目码流 1.5 Gbps ~ 3.0 Gbps，百兆网口直接被击穿，千兆网口也会被挤爆并连带运动卡顿。看到 /image_left_raw/h265 这个名字里的 h265，就该知道必须先解码。

示例采用“一包一解”的最小实现：每收到一个 H.265 字节包，就打开、解码并返回第一帧。return img 写在 for 循环内部，因此函数只会返回解出的第一帧，这也是它适合做单帧取图的写法。

一旦关键点可信，动作语义就浮出来了：肩、肘、腕与髋、膝、踝之间的相对距离和夹角，足以区分下犬式、站立、深蹲这类姿态。但前提是——你得先把置信度算对。

⚠️ 最易踩坑点：关键点置信度是 Logit，非概率！

许多开发者在过滤噪点时直接写 if point.confidence > 0.5，结果发现所有点都被过滤掉了。原因很直接：官方接口返回的 confidence 字段是未经激活函数计算的原始 Logit 实数值！必须通过 Sigmoid 函数映射为 [0.0, 1.0] 区间：

Probability = 11 + e−logit Sigmoid：把无界的原始 Logit 压进 (0, 1) 区间，logit = 0 时概率恰好是 0.5
原始 confidence 字段（Logit）无界实数，可以为负，也可以远大于 1
−100+10
Sigmoid 之后的概率有界区间 [0.0, 1.0]，阈值 0.5 ↔ Logit 0

同一条阈值判据，在两种读法下结论可能完全不同：

🚨 典型症状：所有关键点都被过滤空Logit 落在 0 ~ 0.5 之间时，真实概率已经在 50% ~ 62% 上下，但 confidence > 0.5 会把它当成“低置信”全部丢掉。表里 Logit = 0.3 那一行，就是这类误杀的现场。

Python 提取标准示例

订阅到 /perception/poses 后，按下法逐点做 Sigmoid，再把 x、y 与还原后的概率一起打包：

python 
import math

def extract_keypoints(pose_msg):
    """解析 17 点骨骼关键点并还原真实置信度概率"""
    parsed_people = []

    for person in pose_msg.persons:
        kps = []
        for raw_kp in person.keypoints:
            # 执行 Sigmoid 转换
            prob = 1.0 / (1.0 + math.exp(-raw_kp.confidence))
            kps.append({
                "x": raw_kp.x,       # 像素坐标 X
                "y": raw_kp.y,       # 像素坐标 Y
                "prob": prob        # 真实概率 (0.0 ~ 1.0)
            })
        parsed_people.append(kps)

    return parsed_people

注意返回结构是按人分组的：parsed_people 的每一项对应一个人，每个人是一个关键点列表。后续做动作判定时，请以“人”为单位成组使用坐标，不要把不同人的关节点混进同一个列表。

四、IMU 惯导遥测：100 Hz 的姿态反馈

高频 100Hz 的姿态反馈对于越野平稳控制与跌倒判定至关重要。它同样是一条独立话题，字段不多但每一类都有明确用途：

字段含义用途
linear_acceleration三轴加速度判断冲击、跌落与身体倾斜趋势
angular_velocity三轴角速度判断转向与姿态抖动
orientation四元数姿态机身朝向反馈、稳住越野步态
🧪 初学者自检建议在调试通信环境时，推荐优先订阅 /imu_raw 一条话题进行链路冒烟测试：它的报文体积小、刷新率高，能极快验证 RMW 是否真正通畅。点云和双目解码都可能掩盖链路问题，IMU 不会。
  • 为什么先测它：100Hz 的高频小报文，通不通几秒内就能看出来，不用等一帧 1080P 画面。
  • 它证明什么：RMW 通路、话题名、QoS 订阅关系都对了，再去接点云与视频流就只剩数据处理问题。
  • 它服务谁：越野平稳控制与跌倒判定这两类高频逻辑，直接吃这 100Hz 的姿态反馈。
